### 2026-07-27（iPadで同期失敗＝Firebaseルール有効期限切れの対応）

#### 背景と出発点
実運用フェーズで「PCではクラウド同期できているが、iPadで見ると同期が失敗する。先週までは見れていた」という報告があった。コード変更は伴わず、Firebase側の設定が原因のトラブルシューティングセッションである。

#### 原因究明の過程

**「先週まで見れていた」という手がかり**：
この一言が決定的だった。コードは変えていないのに突然動かなくなった＝コードではなく外部要因（＝Firebaseのセキュリティルールの有効期限切れ）を疑うべきと判断した。

**PCとiPadで挙動が違う理由の推論**：
- PC：以前に同期成功済みで、ブラウザ内（localStorage）にデータのキャッシュが残っている → ルールが切れて同期に失敗しても、キャッシュで表示できてしまう（＝一見「同期できている」ように見える）
- iPad：キャッシュがない（または少ない）ため、同期失敗がそのまま「見られない」形で表面化する

**診断パネルの活用**：
第3セッションで常設した同期診断パネル（`runSyncDiagnosis()`）をiPadで実行してもらい、「ルールの有効期限切れ（permission-denied）」を確認。診断機能を常設していたことがここで役立った。

#### 実際の原因（2つのルールの期限）
ユーザーのスクリーンショットで両方のルールを確認：
- **Firestore**：`allow read, write: if request.time < timestamp.date(2026, 7, 2);` → **7月2日で既に期限切れ**（今日は7月27日）。これが真犯人。
- **Storage**：`... timestamp.date(2026, 8, 1);` → 8月1日期限でまだ切れていなかったが、念のため同時対応。

テストモードで作成したルールは30日間の有効期限付き（`if request.time < timestamp.date(...)`）であり、期限が来ると全アクセスが拒否される仕様。セットアップから約3〜4週間で切れることを失念していた。

#### 対応内容（すべてユーザーがFirebaseコンソールで実施）
Firebaseコンソール操作はユーザー担当（外部Webサービスの管理操作のため）。Claudeは手順とルール文面を提供した。

- **Firestore**：ルールを期限なし（`if true`）に書き換えて公開
- **Storage**：同様に `if true` に書き換えて公開

```
// Firestore
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /{document=**} { allow read, write: if true; }
  }
}
// Storage
rules_version = '2';
service firebase.storage {
  match /b/{bucket}/o {
    match /{allPaths=**} { allow read, write: if true; }
  }
}
```

#### 決定事項・次のタスク
- ルールを `if true`（期限なし）に変更し、今後二度と有効期限切れが起きないようにした
- コード変更はないため今回はcommit/pushなし
- **重要な教訓**：
  - Firebaseの「テストモード」ルールは30日で期限切れになる。テストモードのまま実運用に入ると、忘れた頃に突然全同期が停止する
  - 「コードを変えていないのに急に動かなくなった」場合は、コードではなく外部要因（ルール期限・APIキー・サービス障害）を疑う
  - キャッシュのある端末（PC）とない端末（iPad）で症状が違う場合、クラウド同期の失敗を疑う手がかりになる
  - 常設した診断パネルがトラブル時に有効だった。今後も維持する
- **セキュリティ上の補足（今後の検討事項）**：`if true` は「誰でもアクセス可能」な状態。学校の備品データという性質上リスクは低いが、より厳密にするなら Firebase Authentication を導入し「ログイン必須」ルールにする選択肢もある（現時点では未実施）
